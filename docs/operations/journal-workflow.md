# Manual journal approval and recovery

The journal register and detail page expose the same server-calculated workflow decisions as MCP. Read the journal's `workflow` object for the current status, frozen `contentHash`, `approvalVersion`, ledger `manualPostingMode`, and each action's `allowed`, `reasonCode`, and explanation. The MCP response additionally narrows actions to the connection's scopes, write mode, permissions, and tool overrides, and identifies confirmation requirements.

## Progressing a journal

- **DRAFT:** an authorized user can submit for independent review or use the existing manual posting path. `REVIEW_REQUIRED` leaves newly created manual journals as drafts for user review; it does not remove the existing permission to post a reviewed draft manually. `AUTO_POST` can automatically post eligible user-created journals. Journals generated by asset schedules remain linked to their original schedule and follow the manual journal workflow.
- **SUBMITTED:** content is frozen. An independent user with approval permission reviews the exact hash and version, approves, and then an authorized user posts the approved version. An existing submission retains these approval requirements under both posting policies, including after a ledger switches to `AUTO_POST`.
- **APPROVED:** an authorized user can post the approved hash and version while the period and accounting validations allow it. Approval does not expire merely because the posting policy changes. Creators may post after independent approval, but cannot approve their own journals.
- **POSTED:** normal workflow actions are unavailable. Existing reversal and separately authorized administrative controls continue to apply.

The UI provides the allowed actions on the register and detail page. In MCP, use `finlynq_daily_list_journals` or `finlynq_daily_get_journal`, then the appropriate `finlynq_daily_submit_journal`, `finlynq_daily_approve_journal`, or `finlynq_daily_post_journal` tool. Approval and posting of an approved journal require the exact approval version. Supply the reviewed content hash and audit reason. After each transition, use the refreshed journal and action metadata; if `workflowRefreshRequired` is true, read the journal again.

## Returning a submission for correction

A creator with submission permission may withdraw their own **SUBMITTED** manual journal. A different user with approval permission may reject it. Use the UI controls or `finlynq_daily_withdraw_journal` / `finlynq_daily_reject_journal`. Both require the exact frozen hash and approval version, a reason, and a UUID v4 idempotency key. Keep that key when retrying the same command; use a new key for a new reviewed action. UUID letter case is normalized.

Both operations return the existing journal to **DRAFT**, clear its frozen approval metadata, and retain the journal ID, lines, asset schedule link, and audit history. Rejection also appends an immutable rejection decision. Recovery cannot change the journal's business content in the same operation. Approved, posted, deleted, source-owned, or dependent entries cannot use these recovery actions. Closed periods and periods that exclude the journal's purpose also block recovery.

Every successful submission consumes an increasing approval version, including a submission withdrawn before any reviewer decides. Resubmitting unchanged content therefore produces a new version. Old approval/rejection commands fail with `STALE_VERSION`. Replaying an already completed recovery command reports the current journal state and `idempotentReplay: true` without withdrawing a later submission. Reusing a key with a different journal, actor, hash, version, action, or reason is rejected.

The database enforces the frozen-version, independent reviewer, period, recovery permission, dependency, and immutable audit controls. Existing authentication, organization write activation, MCP confirmation and MFA requirements remain in force. Workflow recovery does not grant administrative unpost/delete authority.

Stable disabled reasons include `CREATOR_CANNOT_APPROVE`, `CREATOR_REQUIRED`, `MISSING_PERMISSION`, `WRITES_DISABLED`, `PERIOD_CLOSED`, `STALE_VERSION`, `POLICY_RESTRICTION`, `HAS_DEPENDENCIES`, `INVALID_CONTENT`, `APPROVAL_REQUIRED`, and `INVALID_STATE`. MCP can also return `CONNECTION_RESTRICTED`. Refresh stale reads, ask an independent authorized approver where indicated, or correct draft content through its owning workflow; recovery never requires a duplicate journal.
