# Tax draft review and retention

Tax input drafts are separate from immutable shared templates, effective configurations, calculated workpapers, canonical selections and external filing. The existing tax mapping, configuration and preparation permissions govern each draft kind. Tax canonical-management permission governs workpaper review, lock and cleanup. No role or connection grant is added.

Save draft stores a complete validated input revision without creating a mapping, activating a configuration or calculating a workpaper. Review changes records the exact entity/ledger/template, effective dates or period, prior mapping/configuration, proposed fields, selected account identities and readiness warnings. Review records the actor and time. Every edit clears approval. Lock version compares the reviewed hash against current dependencies and commits the frozen artifact in the same transaction as its lock revision. Retries use an idempotency key; stale revisions and simultaneous edits cannot silently overwrite one another.

Locked inputs cannot be edited or discarded. Create corrected version retains the original and starts a linked draft. A corrected prepared workpaper creates another immutable calculation in history with `correctionOfFilingId`; it does not automatically replace a canonical workpaper or change the original lifecycle. Selecting a canonical workpaper or archiving/superseding history remains a separate authorized operation. Mapping locks do not activate filing configurations, and no review or lock submits tax returns, posts journals, pays taxes or closes accounting periods.

Filing history and the preparation workspace expose Report actions with exact UUID, source reference, scope, frozen versions, review/lock/export events and dependencies. Move to Trash requires the current preview hash/version, a reason and the literal confirmation `DELETE <uuid>`. Delete and restore require an active organization OWNER role plus `tax.filing.canonical.manage`, checked against live membership in both the write service and database trigger. Other tax managers may still review and lock workpapers but cannot delete or restore them. Role checks also apply before idempotent replays.

An owner can move any report to Trash, including historical imports, legacy reports, reviewed/exported/locked reports, canonical reports and reports with existing dependencies. These conditions are informational rather than deletion blockers. Trash removes the selected report from active reports, filing-history lists and exports while preserving its contents, history and existing links. Related reports are not automatically hidden. The Trash tab supports `RESTORE <uuid>` to restore the same report without changing any stored canonical decision, configuration, journal or accounting-period state. A previously selected report can therefore reappear as canonical if that selection is still current. There is no permanent-deletion operation, and moving a report to Trash does not withdraw an external filing. No existing report is automatically moved by the migration.

All workpaper references and Trash changes share a tenant governance fence. Database triggers also reject new references to hidden records and enforce append-only audit history. Exports recheck visibility under that fence, including repeat exports, and record export history before returning the file. A completed export does not prevent an owner from subsequently moving the report to Trash. The approved synthetic-demo reset registry includes both event tables; private organizations are unaffected.
